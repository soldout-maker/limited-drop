## D-001. Monorepo 도구

- **주제:** pnpm workspace만 쓸지, Turborepo를 함께 쓸지
- **선택지:**
  - A. pnpm workspace만 사용 (`pnpm -r run build`)
  - B. pnpm workspace + Turborepo (작업 순서, 캐시, 병렬 실행)
- **현재 제안:** B (적용됨)
- **결정 이유:** 앱이 3개(web/api/worker)이고 공유 패키지가 의존 관계를 갖기 때문에 빌드 순서 관리와 캐시가 유용함. 설정은 `turbo.json` 하나라서 제거 비용도 낮음.
- **주의:** Windows의 **스마트 앱 컨트롤(Smart App Control)** 이 켜진 PC에서는 `turbo.exe` 실행이 차단됨 (`An Application Control policy has blocked this file`). 이 경우 `pnpm -r run <task>`로 같은 작업을 실행할 수 있음. 팀원 PC에서 문제가 계속되면 A로 바꾸는 것을 고려.
- **결정 상태:** `초기 선택`

## D-002. 언어 / 툴체인 버전

## D-004. 테스트 전략 및 도구

- **주제:** 테스트 범위(단위/통합/E2E)와 도구
- **선택지:** Vitest / Jest (NestJS 기본) / Playwright (E2E) 등
- **현재 제안:**
  - 도구와 범위: 없음 (`결정 필요`). 현재 `test` 스크립트와 CI의 test 단계는 **일부러 추가하지 않음**.
  - 테스트 작성 자동화 방식 (`초기 제안`) — "Claude가 작성·실행, 사람이 확인 후 커밋":
    1. **기준은 요구사항**: 테스트는 구현 코드가 아니라 티켓의 요구사항과 QA 체크리스트에서 도출한다 (구현을 보고 만든 테스트는 버그를 정답으로 굳힐 수 있음).
    2. **로컬 자동화**: `test-writer` 에이전트를 추가하고, `/pr` 스킬에 "연결된 작업/티켓 이슈 읽기 → 테스트 작성·보완 → 실행 → 결과를 PR의 테스트 / 확인에 기록" 단계를 넣는다. 커밋은 사람이 diff를 확인한 뒤 한다.
    3. **CI 게이트**: CI에 `pnpm test`를 추가하고 브랜치 보호의 필수 status check로 지정한다.
    4. **(선택) PR 리뷰 봇**: 필요해지면 GitHub Actions에서 Claude가 "테스트가 빠진 요구사항"을 **코멘트로만** 남긴다. CI에서 테스트를 자동 커밋하거나 별도 PR을 만들지는 않는다.
    - 동시성 시나리오(재고 차감, 대기열 순번, 결제 미완료 처리 등)는 사람이 검증할 상황을 정하고, Claude는 코드 작성을 맡는다.
- **결정 이유:** 2인 팀의 테스트 작성 부담을 줄이되, 사람이 쓰지 않은 코드가 리뷰 없이 쌓이는 것을 막기 위함.
- **결정 상태:** `결정 필요` (자동화 방식은 `초기 제안`) — 도구와 범위가 결정되면 각 패키지에 `test` 스크립트, `turbo.json`에 `test` 작업, CI에 `pnpm test` 단계, `test-writer` 에이전트, `/pr` 스킬 수정을 한 번에 추가한다.

## D-016. PR merge 방식

- **주제:** 브랜치별 PR merge 방식
- **현재 제안:**
  - `feat/*` 등 → `develop`: Squash merge (작업 하나 = 커밋 하나, PR 제목 = 커밋 메시지)
  - `hotfix/*` → `main`: Squash merge
  - `develop` → `main` (릴리스): Merge commit — squash하면 main과 develop의 이력이 어긋나 다음 릴리스 때 충돌이 생기기 쉬움
- **결정 상태:** `초기 제안`

## D-017. API 응답 / 에러 형식

- **주제:** 성공 / 실패 응답의 JSON 모양, 에러 코드 목록, 목록 조회의 페이지네이션 방식
- **왜 중요한가:** web이 모든 API 응답을 같은 방식으로 처리하려면 형식이 하나여야 함. 첫 API가 생긴 뒤 바꾸면 양쪽을 다 고쳐야 함.
- **선택지:**
  - A. 성공은 데이터 그대로, 실패만 `{ code, message }` (NestJS 기본에 가까움)
  - B. 항상 감싸기: `{ data }` / `{ error: { code, message } }`
  - 페이지네이션: offset(`page`, `pageSize`) / cursor
- **현재 제안:** 없음
- **결정 상태:** `결정 필요` — 첫 API 작업 전

## D-019. web ↔ api 타입 공유 방식

## D-023. 상대방 부재 시 긴급 hotfix

- **주제:** `main` 보호 규칙상 상대방 approval이 있어야 merge되는데, 운영 장애가 났을 때 상대방이 연락되지 않으면?
- **현재 상황:** 보호 규칙에 예외(bypass)가 없어서 **두 사람 모두 혼자서는 merge할 수 없음**. 지금은 배포 전이라 문제없지만, 배포 후에는 장애가 길어질 수 있음.
- **선택지:**
  - A. 지금처럼 예외 없음 (항상 상대방을 기다림)
  - B. 저장소 관리자에게 `main` 규칙 예외를 허용하고, `hotfix/*`에만 쓰기로 약속. 사후에 상대방이 리뷰
  - C. 연락이 되면 메신저로 확인받고, 사후 approval
- **결정 상태:** `결정 필요` — 첫 배포 전
