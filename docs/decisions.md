## D-001. Monorepo 도구

- **주제:** pnpm workspace만 쓸지, Turborepo를 함께 쓸지
- **선택지:** A. pnpm workspace만 (`pnpm -r run build`) / B. pnpm workspace + Turborepo (작업 순서, 캐시, 병렬 실행)
- **현재 제안:** B (적용됨). 📝 노션 초안도 Turborepo + pnpm.
- **결정 이유:** 앱 3개 + 공유 패키지의 빌드 순서 관리와 캐시가 유용함. 설정은 `turbo.json` 하나라 제거 비용도 낮음.
- **주의:** Windows **스마트 앱 컨트롤**이 켜진 PC에서는 `turbo.exe`가 차단됨. 이 경우 `pnpm -r run <task>`로 실행.
- **결정 상태:** `초기 선택`

## D-002. 언어 / 툴체인 버전

- **현재 적용:** Node 24 (`.nvmrc`, `engines`), pnpm 11, TypeScript **6.0.x**, ESLint **9.x**, Next.js 16, NestJS 12, React 19
- **결정 이유:** TS 7 / ESLint 10은 typescript-eslint · eslint-config-next가 아직 지원하지 않음. `@nestjs/schematics`는 TS 6 이상 필요. peer dependency 충돌이 없는 조합.
- **결정 상태:** `초기 선택` — 생태계가 따라오면 TS 7 / ESLint 10으로 올림

## D-003. ORM

- **선택지:** Drizzle / Prisma
- **현재 제안:** 📝 원래 계획은 **Drizzle**. 노션 초안: "둘 중 익숙한 쪽으로 빨리 정하는 게 낫다".
- **고려할 점:** Drizzle은 SQL에 가깝고 가벼움 (조건부 업데이트 · 트랜잭션을 직접 쓰기 쉬움). Prisma는 스키마 · 마이그레이션 도구가 편하고 자료가 많음. 둘 다 NestJS와 함께 쓸 수 있음.
- **결정 상태:** `결정 필요` — 화요일 회의. 결정 전까지 DB 관련 코드와 의존성을 추가하지 않음.

## D-004. 테스트 전략 및 도구

- **선택지:** Vitest / Jest (NestJS 기본) / Playwright (E2E)
- **현재 제안:**
  - **범위** 📝: MVP에서는 **재고 차감 · 주문 상태 전이** 테스트를 필수로.
  - **도구**: 없음 (`결정 필요`). `test` 스크립트와 CI의 test 단계는 일부러 추가하지 않음.
  - **테스트 작성 자동화** (`초기 제안`) — "Claude가 작성 · 실행, 사람이 확인 후 커밋":
    1. 테스트는 구현 코드가 아니라 **티켓의 요구사항과 QA 체크리스트**에서 도출한다.
    2. `test-writer` 에이전트를 추가하고, `/pr` 스킬에 "연결된 이슈 읽기 → 테스트 작성 · 보완 → 실행 → PR에 결과 기록" 단계를 넣는다. 커밋은 사람이 diff를 확인한 뒤 한다.
    3. CI에 `pnpm test`를 추가하고 브랜치 보호의 필수 status check로 지정한다.
    4. (선택) PR 리뷰 봇은 "테스트가 빠진 요구사항"을 **코멘트로만** 남긴다.
    - 동시성 시나리오(재고 차감, 대기열 순번, 미결제 처리)는 사람이 검증할 상황을 정하고, Claude는 코드 작성을 맡는다.
- **결정 상태:** `결정 필요` — 도구가 정해지면 `test` 스크립트, `turbo.json`, CI, `test-writer`, `/pr` 스킬을 한 번에 추가.

## D-016. PR merge 방식

- **배경:** 노션 초안(11/14)은 `main` 하나만 쓰는 전략에서 "Squash 통일"이었음. 이후 **`develop`을 쓰는 Git Flow**로 바뀌어서 다시 정해야 함.
- **선택지:**
  - A. **전부 Squash** — 이력이 가장 깔끔. 단, `develop → main` 릴리스를 squash하면 두 브랜치 이력이 어긋나 다음 릴리스에서 이미 배포한 변경이 다시 보이거나 충돌이 생김.
  - B. **작업 PR은 Squash, 릴리스(`develop → main`)는 Merge commit** — 깔끔함과 릴리스 안정성을 같이 챙김. 버튼을 상황에 맞게 골라야 함.
  - C. **전부 Merge commit** — 규칙이 가장 단순하고 이력이 그대로 남음. `develop` 이력에 작은 커밋이 많이 쌓임. (민성님 선호)
- **결정 상태:** `결정 필요` — 화요일 회의. 결정되면 저장소의 허용 merge 방식도 맞춰 바꿈 (현재 Squash, Merge commit 둘 다 허용).
