# /ticket

이 프로젝트는 **티켓 → 작업 → QA → 완료** 흐름을 따른다 ([docs/workflow.md](../../../docs/workflow.md)).

| 종류 | 질문                        | 템플릿                                | label    |
| ---- | --------------------------- | ------------------------------------- | -------- |
| 티켓 | 무엇을, 왜?                 | `.github/ISSUE_TEMPLATE/1-ticket.yml` | `ticket` |
| 작업 | 구현하려면 무엇을? (PR 1개) | `.github/ISSUE_TEMPLATE/2-task.yml`   | `task`   |
| QA   | 요구사항대로 동작하는가?    | `.github/ISSUE_TEMPLATE/3-qa.yml`     | `qa`     |

## 절차

1. 종류를 판단한다. 인자가 없으면 요청 내용으로 판단하고, 애매하면 묻는다.
2. 해당 템플릿 파일을 읽고 **같은 섹션 제목**으로 본문을 작성한다.
3. 종류별 작성 기준:
   - **티켓**: 목적과 요구사항만 쓴다. 구현 방법(API 경로, 테이블, 라이브러리)은 쓰지 않는다. 정책이 불분명하면 `참고 / 미결정 사항`에 질문으로 남긴다.
   - **작업**: 상위 티켓 번호를 받아 `gh issue view <번호>`로 읽고, PR 하나로 끝낼 수 있는 크기로 나눈다. 영역(web/api/worker/packages)을 표시한다. 여러 개면 목록으로 먼저 보여준다.
   - **QA**: 상위 티켓의 요구사항 하나하나를 검증 가능한 체크 항목으로 바꾼다. 정상 경우와 실패/경계 경우를 모두 넣는다.
4. [docs/decisions.md](../../../docs/decisions.md)에서 `결정 필요`인 기술에 의존하는 내용이면 이슈에 그 사실을 적는다 (예: "D-003 ORM 결정 필요").
5. **초안을 사용자에게 먼저 보여주고 확인을 받는다.** 확인 후에만 생성한다:

   ```bash
   gh issue create --title "[티켓] ..." --label ticket --body-file <임시파일>
   ```

   label이 없어서 실패하면 사용자에게 알리고 label 없이 생성할지 묻는다.

6. 작업 이슈를 만들었으면 상위 티켓의 `작업 목록`에 링크를 추가할지 묻는다.

## 제목 형식

- `[티켓] 판매자가 상품 드롭을 등록할 수 있어야 한다`
- `[작업] Drop 생성 API 구현`
- `[QA] 드롭 등록`
